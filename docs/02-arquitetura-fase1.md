# Arquitetura e estado da fase 1

Data: 2026-10-30. Stack: .NET 9, WPF, CommunityToolkit.Mvvm. Licença GPL-3.0.

## Ecossistema de pastas (criado na primeira execução)

```
<raiz escolhida pelo usuário>/
  hub.json           ferramentas instaladas no escopo do hub, último projeto aberto
  tools/<id>/        uma pasta por ferramenta (DSPRE, melonDS, NitroPaint, PokEditor, apicula, Tinke)
  runtimes/          reservado para JRE gerenciado (fase posterior)
  cache/<id>/<tag>/  downloads das releases, reaproveitados em reinstalação
  logs/              reservado
  projects/<nome>/
    project.json     jogo base, game code, geração, ferramentas de escopo de projeto
    base.nds         dump do usuário, nunca alterado
    workspace/       ROM extraída, fonte única da verdade (extração vem na fase 2)
    builds/          ROMs geradas; ${rom} aponta para a mais recente
    decomp/<id>/     clones das decomps da pret
```

O caminho da raiz fica em `%AppData%\PokeHub\settings.json`.

## Módulos do Core

| Pasta | Responsabilidade |
|---|---|
| `Hub/` | `HubPaths` (layout), `HubConfig` (hub.json), `HubBootstrapper` (primeira execução) |
| `Rom/` | `NdsRomHeader` (lê título e game code), `GameInfo` (game code → jogo, geração, região) |
| `Projects/` | `ProjectConfig`, `ProjectPaths`, `ProjectService` (criar, listar, abrir) |
| `Plugins/` | `PluginManifest` (modelo do JSON), `PluginCatalog`, `GitHubReleaseClient`, `PluginInstaller` |
| `Processes/` | `ProcessRunner` (comandos até o fim, com log), `ToolLauncher` (abre ferramenta com variáveis resolvidas) |

## Manifesto de plugin (plugins/*.json)

- `contexts`: em quais telas aparece (maps, events, scripts, trainers, pokemon, text, graphics, models, audio, emulator, decomp, utility)
- `generations`: filtro pelo projeto aberto. **GEN5:** adicionar 5 nos plugins que servem Gen 5
- `scope`: `hub` (tools/) ou `project` (projects/x/decomp/)
- `source.type`: `gitHubRelease` (assetPattern + executable), `gitClone`, `system` (usuário aponta o exe)
- `launch.runtime`: vazio = exe direto, `java` = `java -jar`
- Variáveis nos args: `${project}` `${workspace}` `${baseRom}` `${rom}` `${builds}` `${decomp}` `${tool}` `${hub}`

## Fase 2 (em andamento)

Feito em 2026-10-30:

1. Extração de `base.nds` para `workspace/` e empacotamento em `builds/` em C# puro (`Rom/NdsExtractor`, `Rom/NdsPacker`, `Rom/NdsFileSystem`). Layout igual ao do ndstool: `header.bin`, `arm9.bin` (com nitro footer), `arm7.bin`, `y9.bin`, `y7.bin`, `overlay/overlay_NNNN.bin`, `banner.bin`, `data/`. Extras do hub: `fnt.bin` (FNT original) e `nds-layout.json` (árvore ordenada e ids).
   - Árvore de `data/` inalterada: a FNT original é reaproveitada, ids idênticos aos da ROM.
   - Árvore alterada: FNT reconstruída preservando a ordem conhecida; arquivos novos entram no fim da própria pasta.
   - Secure area do arm9 copiada sem decifrar (nenhuma chave da BIOS no projeto). O CRC da secure area do header original é preservado enquanto os bytes 0x4000..0x7FFF não mudarem (dumps de cartucho têm os 8 primeiros bytes destruídos, então recalcular nunca bate com o original).
   - `header.bin` guarda os 0x4000 bytes iniciais e `nds-layout.json` guarda a ordem física dos arquivos, então o reempacotamento de uma árvore inalterada é **byte a byte idêntico** ao dump original até o tamanho usado (validado com SoulSilver USA em 2026-10-30; teste opcional `POKEHUB_REAL_ROM=<caminho.nds>`).
   - Novo projeto extrai automaticamente. Botões: Extrair ROM, Empacotar, Empacotar e rodar.
2. "Empacotar e rodar" abre a ROM recém-gerada no melonDS, se instalado.

3. JRE gerenciado (`Runtimes/RuntimeManager`): requisitos `java21`/`java17` nos manifestos são instalados em `runtimes/<id>` a partir da API do Adoptium (Temurin JRE, Windows x64) junto com a ferramenta. O lançador usa esse java.exe; sem ele, cai no `java` do PATH. Registrado em `hub.json` → `installedRuntimes`.

4. Build das decomps (`Decomp/UnixShell`, `Decomp/DecompBuildService`): detecta MSYS2 (pastas usuais) e distros do WSL, roda o `build.command` do manifesto (`make rom`) na pasta do clone e copia `build.output` para `builds/`. MSYS2 tem prioridade porque o clone fica no disco do Windows e o WSL é lento em `/mnt`. Correção ao levantamento: as decomps baixam o compilador sozinhas (`tools/devtools/get_metroskrew.sh` puxa o pacote metroskrew de mid-kid/metroskrew), então o usuário não fornece o mwcc. O que ele precisa é um shell Unix com as dependências do INSTALL.md.

5. Git gerenciado e versionamento do workspace (`Runtimes/RuntimeManager` + `Projects/WorkspaceGit`): ao iniciar, o hub procura git no PATH e em `runtimes/git`; se não há, oferece instalar o MinGit portátil (release do git-for-windows, 64 bits, sem busybox). O `workspace/` vira um repositório git (identidade fixa PokeHub, `* binary`) com commits automáticos: na extração, antes de empacotar e ao fechar uma ferramenta aberta pelo hub. Botões "Salvar versão" e "Versões" na barra superior; `WorkspaceGit.RestoreAsync` já existe para voltar a uma versão, sem UI ainda.

6. Checagem de dependências (`Runtimes/DependencyChecker`): `dotnet-framework-4.8`/`4.5` pelo valor Release em `HKLM\SOFTWARE\Microsoft\NET Framework Setup\NDP\v4\Full` (528040 = 4.8, 378389 = 4.5), `vcredist-x64` por `HKLM\SOFTWARE\Microsoft\VisualStudio\14.0\VC\Runtimes\x64`. O card mostra cada requisito com estado (em vermelho se falta) e, ao instalar ou abrir, oferece abrir a página oficial de download. Esses instaladores exigem admin, por isso o hub não os executa. Requisitos desconhecidos continuam informativos.

7. Janela "Versões" (`Views/HistoryWindow`): lista os commits do workspace e restaura o selecionado. O estado atual é commitado antes de restaurar e de novo depois, então o histórico nunca perde nada. A versão mais recente não é restaurável por ser o estado atual.

## Fase 3 (em andamento)

1. **Workspace no formato ds-rom** (2026-10-30). O DSPRE 2.x abandonou o layout ndstool: usa o ds-rom (AetiasHax/ds-rom, MIT, Rust) e oferece converter pastas antigas. Para o DSPRE abrir o workspace sem conversão, o hub passou a extrair com o ds-rom (`Rom/DsRomTool`, runtime `dsrom` instalado da release do GitHub, 5 MB). Layout: `config.yaml`, `header.yaml`, `arm9/` (descomprimido, itcm/dtcm separados), `arm9_overlays/` (descomprimidos), `arm7/`, `banner/`, `files/`, `path_order.txt`. O hub grava ao lado um `pokehub-workspace.json` com SHA-1 do dump e o CRC original da área segura: o `dsrom build` zera esse CRC, e o hub o restaura quando a área segura não mudou. Validado: reconstrução byte a byte idêntica ao dump de SoulSilver (teste opcional com `POKEHUB_REAL_ROM` + `POKEHUB_DSROM`). O extrator/empacotador em C# continua como reserva (formato "ndstool legado") se o ds-rom não puder ser baixado.

4. **Editor de treinadores embutido** (`Core/Gen4/*`, `App/Views/TrainerEditorWindow`, manifesto `trainer-editor.json` com `source.type = builtin`). Primeiro editor próprio do hub:
   - `Narc`: leitura e escrita de NARC (BTNF preservado, arquivos alinhados a 4 bytes com 0xFF).
   - `Gen4TextArchive` + `CharMap`: bancos de texto de Gen 4 (cifra da tabela de offsets e das strings, compressão de 9 bits dos nomes de treinador) com o `charmap.json` do DSPRE embutido. Mensagens não alteradas são regravadas com as palavras originais, porque o encoder da Nintendo deixa bits de preenchimento diferentes.
   - `Gen4Game`: caminhos dos NARCs e números dos bancos de texto por jogo e idioma (DP, Pt, HGSS; fonte: RomInfo do DSPRE).
   - `Trainer`/`PartyMember`: registro de 20 bytes do trdata e entradas do trpoke (6/8/14/16 bytes em DP, +2 de ball seal em Pt/HGSS), com os bytes originais preservados quando o treinador não muda.
   - `TrainerRepository`: carrega treinadores e as listas de nomes de classes, espécies, itens e golpes do próprio jogo; grava trdata, trpoke e o banco de nomes.
   - A janela lista os treinadores com filtro, edita nome, classe, IA, tipo de batalha, itens e o time (espécie, forma, nível, dificuldade/IVs, item, golpes, ball seal, flags de gênero e habilidade). Salvar grava no workspace e cria uma versão no git.
   - Validado com SoulSilver: carregar e regravar sem mudanças produz NARCs idênticos (teste opcional `POKEHUB_WORKSPACE=<workspace>`).
   - Fora do escopo por enquanto: adicionar treinadores novos (exige expandir tabelas no arm9), nomes de classe, editar sprites.
   - Exibição da sprite (`Gen4/TrainerSprites`, só leitura): 5 arquivos por classe em HGSS `a/0/5/8` ou DP/Pt `poketool/trgra/trfgra.narc`; usa o NCBR (`classe*5+4`, faixa de 2 quadros, 4 bpp em linhas, cifrada com o LCRNG; no SoulSilver a semente é a última palavra) e a paleta `classe*5+1`. O sentido da cifra é escolhido pela leitura mais coerente, porque DP/Pt não foram validados com ROM.

5. **MSYS2 instalado pelo hub** (runtime `msys2`, manifesto `msys2.json` com `source.type = runtime`). Baixa o pacote auto-extraível `msys2-base-x86_64-latest.sfx.exe` (40 MB) da release do msys2-installer, extrai em `runtimes/msys2/msys64` com `-y -o` (sem instalador, sem administrador) e prepara a toolchain como o CI do MSYS2 faz: login shell inicial, `pacman --noconfirm -Syuu` duas vezes e `pacman -S --needed` com os pacotes do INSTALL.md das decomps (lista em `setup.pacman` do manifesto). O MSYS2 do hub tem prioridade na detecção. O card aparece na aba Decomp; "Instalar" faz tudo num clique e, já instalado, "Preparar toolchain de novo" só refaz a preparação.
   - Lições do build real do pokeplatinum pelo hub (2026-10-30): (a) o `/etc/profile` só roda os scripts de primeira execução (chaveiro do pacman etc.) com `MAYBE_FIRST_START=true`, que o hub passa na primeira chamada; (b) o profile redefine PATH e PKG_CONFIG_PATH, então eles são exportados dentro do comando; (c) o INSTALL.md esquece o `pkg-config` (pacote `pkgconf`) na lista do MSYS2; (d) as ferramentas nativas da decomp usam APIs POSIX e só compilam com o gcc do msys (ambiente `MSYS`, não `UCRT64`); (e) a libpng do mingw64 sugerida pelo INSTALL.md derruba o `nitrogfx` com segmentation fault, porque ele passa `FILE*` do runtime msys para uma libpng de outro runtime. Como o repositório msys não tem libpng, o hub compila uma libpng estática (tarball oficial, `--disable-shared`) em `/usr/local` e aponta `PKG_CONFIG_PATH` e `PKG_CONFIG_PATH_FOR_BUILD` para lá. (f) a libpng estática precisa de `-lz` em `Libs` do `.pc` (não só em `Libs.private`), senão o link do nitrogfx falha. **Validado em 2026-10-30: `make rom` do pokeplatinum completo pelo MSYS2 do hub, 16.680 passos em 48,6 min nesta máquina, ROM de 128 MB copiada para `builds/`.** O primeiro build é lento por reconstruir o jogo inteiro; os seguintes são incrementais (teste opcional `POKEHUB_MSYS2_HUB_ROOT` + `POKEHUB_DECOMP_BUILD=pokeplatinum`).

15. **Dores da comunidade, primeira leva** (2026-10-31): operações simples que não tinham ferramenta.

   - Lição: processos filhos do Core precisam de stdin próprio (`ProcessRunner`), senão a captura trava quando outro leitor segura o stdin do processo (servidor MCP).

16. **Mapa visual no editor de Pokédex** (2026-10-31). `Core/Graphics`: decodificadores LZ10, NCLR (paleta BGR555), NCGR (tiles 4/8 bpp) e NSCR (tilemap com espelhos e banco de paleta) com renderização para RGBA. `Core/Gen4/PokedexAreaMap`: primeira versão usou o tilemap da própria tela de áreas (`a/0/6/8`, NSCR 86), que é simplificado e ficou feio; a versão final usa o **mapa do Pokégear** lido da ROM (`a/1/4/4` = pgmap_gra do pokeheartgold: NSCR 11 + NCGR 10 + NCLR 20, tilemap 512×512 do qual as 20 linhas de cima são o mapa; as cidades aparecem como quadrados porque os ícones são sprites). As posições das áreas vêm da tabela `sLocationSpecs` do Pokégear (x, y, largura, altura em tiles de 8 px por mapa), ligada às áreas da Pokédex por `sOverworldMapIDs`/`sDungeonMapIDs`; como essa tabela fica dentro do overlay 101 e não num arquivo de dados, ela está embutida em `pokedex-areamap-hgss.json` (só números, gerados da decomp, com aliases para os 13 mapas sem entrada direta, ex.: Dragon's Den → Blackthorn). O editor mostra o mapa em 2×, com as áreas marcadas do bloco escolhido em amarelo e contorno só na área sob o mouse; clicar alterna o checkbox. Validado com SoulSilver (Route 29 em x=18, y=14, 3×1). Nada de imagem da Nintendo no repositório. `--screenshot ... --editors` captura também essa janela.

17. **Mapa de eventos** (2026-10-31; card "Eventos e scripts", manifesto `event-map`, só leitura). `Core/Gen4/Scripts`: `ScriptCommandTable` (scrcmd.json do pokeheartgold embutido: nome e tipos de argumento de 853 comandos; "message" 1 byte, "script"/"movement" 4 bytes relativos ao fim do argumento, demais tipos nomeados 2 bytes), `ScriptFile` (tabela de offsets terminada por 0xFD13; desmonta seguindo saltos e chamadas sem repetir; scripts com id acima da tabela são os padrão do jogo), `MapScriptHeader` (level scripts: tipo 1 = tabela variável/valor/script), `EventFile` (placas 20 bytes, NPCs 32, warps 12, triggers 16, contagens u32), `FlagNames` (flags.h/vars.h embutidos: 2912 flags salvas, variáveis 0x4000..0x416F) e `EventMap`, que cruza tudo por mapa (cabeçalho: scripts a/0/1/2, eventos a/0/3/2, banco de texto) e resume cada evento em termos de jogo: flags ligadas/desligadas/conferidas, variáveis gravadas/comparadas, itens, Pokémon, batalhas, warps, primeiras falas; NPC com flag de ocultação e trigger com condição de variável. Uso de cada flag/variável e **faixas livres** (sem uso em scripts e sem nome na decomp). SoulSilver: 478 mapas, 4464 eventos em 0,6 s; 1611 flags livres (maior faixa 0x51F–0x960), 85 variáveis livres. Janela com abas Mapas e eventos (busca por mapa, id 0x... ou fala), Flags e Variáveis (filtro Todas/Usadas/Livres). MCP: `list_events`, `find_events`, `free_flags`, `flag_usage`.

18. **Seletor visual de Pokémon** (2026-10-31; `App/Views/SpeciesPicker`, `App/ViewModels/SpeciesCatalog`, `Core/Gen4/PokemonSprites`, `SpriteStrip`). Substitui as listas de espécie em treinadores, encontros e lote: sprite, busca por nome ou número, setas e Enter. Sprites em HGSS `a/0/0/4`, DP `poketool/pokegra/pokegra.narc`, Pt `pl_pokegra.narc`: 6 arquivos por espécie (costas fêmea e macho, frente fêmea e macho, paleta normal e shiny), mesmo formato da sprite de treinador; no SoulSilver a semente de Pokémon é a primeira palavra e a de treinador é a última. Imagens decodificadas sob demanda, com cache por janela. No cartão do time a sprite respeita forma e "forçar fêmea" (HGSS `a/1/1/4`, Pt `pl_otherpoke.narc`, numeração das decomps; as paletas do Pt ficam 4 arquivos antes, porque ele não tem o Pichu de orelha espigada; DP numera esse NARC de outro jogo e cai na imagem padrão). O item segurado mostra o ícone (`Gen4/ItemIcons`: a tabela `sItemIndexMappings` é localizada no arm9 pelo começo dela, os itens 1 a 3, sem endereço por versão). No editor de treinadores, o cartão do time mostra a sprite, as 11 flags de IA viram caixas de marcar (nomes da decomp pokeplatinum, sincronizadas com o hexadecimal) e a dificuldade tem controle deslizante. Validado com SoulSilver por automação de interface (`System.Windows.Automation`): busca, teclado, mouse, Esc, clique fora, flags, deslizante, forma, encontros (troca de rota em 0,12 a 0,23 s, com 66 seletores) e lote. Sprites, formas, treinadores e ícones também conferidos a olho em SoulSilver e Platinum US (ROM gerada pela decomp). DP sem validação com ROM.

21. **Teclas do melonDS** (2026-10-31; hook `melonds-default-keys`, `Plugins/MelonDsKeys`). O padrão do melonDS é -1 em todas as teclas, então numa instalação nova o jogo só responde ao toque. Ao abrir, o hub grava um mapeamento em `[Instance0.Keyboard]` do `melonDS.toml`, ao lado do executável, só enquanto nenhum botão estiver configurado: atalhos, joystick e teclas escolhidas pelo usuário não são tocados.

20. **Mapa de eventos com planta e Map Studio** (2026-10-31). `Gen4/Scripts/MapLayout`: a matriz do mapa (`a/0/4/1`: largura, altura, nome, cabeçalhos, altitudes e terreno por célula) diz quais células pertencem ao cabeçalho, e cada arquivo de terreno (`a/0/6/5`: 16 bytes de tamanhos, seção de sons de fundo no HGSS, depois 32×32 tiles de tipo e colisão) vira a planta. As posições dos eventos contam do canto da matriz inteira. A janela mostra a planta ao lado da lista: clicar num marcador seleciona o evento, clicar num warp abre o destino. Só HGSS, como o resto do mapa de eventos. Catálogo: `pdsms` (Pokémon DS Map Studio 2.2, zip da release; abre pelo `.bat`, com `JAVA_HOME` apontando para o runtime novo `java8`). Sem licença declarada, então só instalar e abrir. Exportar `.nsbmd` exige o `g3dcvtr.exe`, do kit da Nintendo, que não vem no pacote nem é baixado pelo hub. Instalação e abertura testadas pelo hub (a janela sobe com o Java 8 gerenciado); desenhar e exportar, não. Warp com destino `0xFFF` é dinâmico: volta ao lugar de onde o jogador veio. No SoulSilver, nenhum dos 1.317 warps, 1.034 placas e 195 gatilhos cai fora da planta, e os outros destinos existem; placas costumam estar em tile bloqueado porque ficam em objetos sólidos.

19. **Injeção de código** (2026-10-31; card "Injeção de código", guia `35-injecao-codigo`, `Core/CodeInjection`, só workspace ds-rom). Patches em `workspace/code-patches/<nome>/` (`patch.json` + fontes C/assembly), portanto dentro das versões do projeto; a saída da compilação fica em `code-patches-build/`, fora do workspace.
   - **Memória:** usa a expansão do ARM9 do DSPRE (uma chamada no `Main()` carrega um arquivo de NARC em `0x023C8000`), para continuar compatível com os patches de toolbox dele. Arquivo: HGSS `a/0/2/8` nº 0, DP/Pt `data/weather_sys.narc` nº 9, 88 KB. O hub usa só `0x2000..0x11000` (60 KB) e recusa gravar em área não zerada.
   - **Tabela do DSPRE 2.3.4:** duas entradas alemãs estão erradas (salto de DP aponta para Pt; endereço de HGSS `0x02110B00` no lugar de `0x021110B0`). O hub calcula o salto e corrige o endereço; os testes conferem o BL interno da rotina.
   - **Compilação:** `arm-none-eabi-gcc` do MSYS2, executado direto, Thumb para ARM946E-S, sem biblioteca C, um link por patch com `--gc-sections`. Lição: símbolo do jogo definido no script do ligador não tem tipo e vira ARM mesmo com endereço ímpar, gerando um veneer que trava o jogo; por isso os símbolos vão num `.s` gerado com `.type %function`. Símbolos lidos com `readelf`, porque o `nm` esconde o bit Thumb.
   - **Ganchos:** `call`, `jump` (sem sujar registradores), `pointer`, `bytes`, em `arm9` ou `overlay:N`, com `expect` opcional. Tudo é montado em memória: erro de compilação ou checagem não grava nada. `applied.json` guarda original e gravado de cada trecho, para desfazer antes de reaplicar; se os bytes mudaram por fora, o hub para.
   - **Validado** com SoulSilver US no melonDS: gancho no laço principal alterando o brilho das duas telas, abertura inteira até o menu, comparado com a ROM limpa. Platinum US também, da abertura até a introdução de novo jogo (gancho em `0x02000D84`, ROM da decomp): lá a área da rotina de carga guarda a mensagem de assert do SDK, que o patch do DSPRE sobrescreve e o hub aceita. DP e outros idiomas sem validação com ROM. Janela e ferramentas MCP testadas de ponta a ponta num hub temporário (criar, ativar, aplicar, erros, remover, empacotar e rodar). O arquivo substituído no HGSS é um gráfico original (NCLR), o mesmo que o DSPRE substitui; nem a decomp nem os binários mostram código que carregue o pacote `a/0/2/8`, então parece sem uso, mas uma referência indireta por tabela não está descartada.
   - MCP: `list_code_patches`, `create_code_patch`, `apply_code_patches`, `revert_code_patches`. Teste opcional que gera a ROM: `POKEHUB_INJECT_WORKSPACE` + `POKEHUB_DSROM` + `POKEHUB_MSYS2_HUB_ROOT` + `POKEHUB_INJECT_OUTPUT`.

22. **Pacote de melhorias** (2026-10-31). Prévia do texto com a fonte do jogo e aviso de linha longa (`Gen4/TextPreview`). Editor de stats (`Gen4/PersonalRepository`, card "stats"): lê e grava direto nos 44 bytes, então TMs e o resto continuam iguais. Áreas da Pokédex no Platinum: formato de `pokedex_enc_data.c`; o jogo não guarda nomes, então os da tabela vêm de cruzar cada id com os encontros de cada mapa (o mapa clicável segue só em HG/SS, e os ids 21 e 50 não têm encontro para dar nome). 23. **Tabelas do jogo e tema único** (2026-10-31; card "Tabelas do jogo", `Gen4/GameTables`, `App/Views/GameTablesWindow`). Um editor só, com colunas definidas por tabela: golpes, itens, golpes aprendidos, evoluções, golpes de ovo (só HG/SS), filhotes, altura e peso, trocas, Pokémon do Battle Frontier e valores de scripts ficam em arquivos; TMs, compatibilidade de TMs, lojas, tutores (só HG/SS) e tabela de tipos dependem do arm9 ou de overlays, então só aparecem em ds-rom. Tudo lê e grava nos bytes, então o que não tem coluna fica igual. Lojas, HMs, tutores e tipos são achados pela forma dos dados, e não por endereço fixo: funciona em qualquer idioma e depois de editar. Em scripts só mudam valores de argumentos; inserir comandos exigiria recalcular os saltos do arquivo, e isso segue no DSPRE. O tema do hub entra em cada janela pelo `App.ApplyTheme`, porque no nível do aplicativo o estilo de TextBlock invadiria os modelos dos controles. MCP: `list_tables`, `list_table_owners`, `get_table_rows`, `set_table_cell`.

24. **Editor de scripts e mais tabelas** (2026-10-31; card "Editor de scripts", `Gen4/Scripts/ScriptEditor`, `ScriptArchive`). Inserir e remover comandos reescreve o arquivo e recalcula a tabela de entradas e todos os saltos alcançados; quem saltava para o ponto de inserção executa o comando novo primeiro. Dados de movimento continuam alinhados em 4 bytes com preenchimento logo antes deles. Bytes que nenhuma entrada alcança são copiados como estão, então código morto com saltos próprios não é corrigido. Validado inserindo e removendo comando em todos os arquivos de SS e Platinum: o comportamento se mantém e o arquivo volta idêntico. MCP: `get_script`, `insert_script_command`, `remove_script_command`. Tabelas novas: Headbutt e Safari (só HG/SS, sem árvores nem bônus), treinadores do Frontier, loja comum, posição dos sprites, tutores (cacos) e golpes de ovo (lista no overlay 5) no Platinum.

25. **Pokéathlon e concursos** (2026-10-31; tabelas `pokeathlon` e `contestOpponents`). Pokéathlon: `a/1/6/9`, 20 bytes por registro (`PokeathlonBasePerformance`, ordem Força, Resistência, Salto, Técnica, Velocidade), espécies a partir do Bulbasaur e depois formas. As provas ficam no código, ainda só em parte decompilado. Concursos (só Platinum): `contest_data.narc`, membro 0, 96 oponentes de 48 bytes; o formato não está documentado na pokeplatinum, então só espécie e golpes foram deduzidos e conferidos (Sparky é um Pikachu com Thunder Shock). Os outros membros seguem sem significado conhecido.

26. **Novo evento** (2026-10-31; card "Novo evento", `Gen4/Scripts/NewEventService`, só HG/SS). Cria um NPC completo: mensagens acrescentadas no fim do banco do mapa, script novo no fim do arquivo (`ScriptEditor.AddEntry`, a tabela cresce 4 bytes e as entradas antigas são ajustadas) e objeto no fim da lista do arquivo de eventos (`EventFile.AddObject`). Modelos Falar e Dar item, no mesmo formato dos NPCs do jogo. A flag do item vem da faixa entre as de treinador e as do sistema, sem uso em script. A altura copia o NPC mais próximo, porque o terreno 3D não é lido. Modelo Pokémon no mapa: sprite de quem segue o jogador (`follower-sprites-hgss.json`, gerado de `sprites.h`), grito, `WildBattle` e, se some, flag no objeto mais `HidePerson` ao voltar da batalha; o jogo usa um level script para esconder antes de a tela aparecer, então aqui o Pokémon pode ser visto por um instante. Movimento: `MOVEMENT_TYPE` com alcance em `XRange` e `ZRange`. Modelo Trocar Pokémon: mesmo script dos NPCs de troca do jogo, numa vaga de `a/1/1/2` que nenhum script carrega; o apelido fica no banco de texto 200. Falta: Platinum, editar e remover. MCP: `create_npc`, `create_pokemon_encounter`, `create_trade_npc`.
